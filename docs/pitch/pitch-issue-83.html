Today's Limitation

For a single team, this works perfectly. For a large enterprise, it doesn't scale.

Current Model

cvt serve — single deployment
infrastructure shared server required
storage PostgreSQL / SQLite
blast radius all teams, one instance
registry integration gRPC registration only
enterprise reality

Enterprise Requirements

Hundreds of teams
Each team owns their schema and consumers independently
Existing schema registries
Homegrown, GitHub Enterprise, internal registries already in use
Git as source of truth
Contracts should live in repos, not in a separate database
Zero shared infrastructure
Teams should be able to validate without a running CVT server
Every enterprise adopting CVT hits this gap immediately. The database isn't optional — it's a blocker.

The current architecture is the right design for a single team or small org. These new models extend it for enterprise scale without replacing anything.

Three Deployment Models

Existing Model

Server (Unchanged)

Teams using cvt serve with PostgreSQL or SQLite continue exactly as before. New models add options — they do not change or replace this model.

Best for: Teams already running cvt serve who want a shared registry with consumer management.
Model A

CLI-Only

Teams run cvt validate, cvt compare, cvt generate in CI pipelines. Schemas pulled from any URL or file. No server, no database, no shared state.

Best for: Teams that want schema validation and breaking change detection with zero infrastructure.
Model B

Git-Native

Contracts and schemas live as files in git repos. Teams choose where contracts are stored — centralized repo, consumer repos, or a mix. CVT reads from wherever they are.

Best for: Cross-team contract validation with minimal infrastructure, using git as the source of truth.

New models add options — nothing that works today breaks.

The key design principle: backward compatibility is absolute. No flags change meaning, no existing behavior changes. Teams opt in to new models explicitly.

New Package Boundary

pkg/contracts is a new package that imports pkg/cvt — not the other way around. This keeps the dependency direction clean. The file backend is a new peer of sqlite/postgres/memory, not a special case.

Pluggable Schema Sources

Interface

pkg/cvt/provider.go 
type SchemaProvider interface {
    Scheme() string

    Fetch(
        ctx context.Context,
        ref string,
    ) ([]byte, error)

    FetchVersion(
        ctx context.Context,
        ref     string,
        version string,
    ) ([]byte, error)
}

// FetchVersion required for offline
// can-i-deploy to compare schema
// versions without a running server.

Built-in Providers

Scheme Example Status

or just ./openapi.yaml		 existing

github:// github://org/repo/
openapi.yaml@main		 new
registry:// registry://payments-api
@1.0.0		 new

github:// and registry:// are optional convenience wrappers. Any schema reachable via HTTPS works with https:// directly — no provider needed.

The interface is minimal by design: three methods, no configuration in the interface itself. Config for things like auth tokens lives in .cvt/config.yaml and is picked up by the provider at initialization time.

Acknowledged Breaking Changes

Sometimes you need to ship a breaking change and coordinate the migration.

Without acknowledgment — blocked

Terminal
$ cvt can-i-deploy \
  --schema payments-api \
  --version 2.0.0 \
  --contracts-dir ./consumers/
 
Reading 3 contract files...
✓ checkout-service 3.1.0 compatible
✗ billing-service 2.0.0
  GET /payments/{id}: field
  'amount' type string → number
✗ reporting-svc 1.5.0
  DELETE /payments: endpoint removed
 
✗ Cannot deploy. 2 consumers would break.

With acknowledgment + notify — proceeds

Terminal
$ cvt can-i-deploy \
  --schema payments-api \
  --version 2.0.0 \
  --contracts-dir ./consumers/ \
  --breaking-change-acknowledged \
  --notify
 
✗ billing-service BREAKING (acknowledged)
✗ reporting-svc BREAKING (acknowledged)
 
Notifying affected consumers...
  → Issue #412 opened: org/billing-service
  → Issue #88 opened: org/reporting-svc
  → Webhook fired: hooks.internal/cvt
 
⚠ Deploying. 2 consumers notified.
--breaking-change-acknowledged
Bypasses the safety gate — allows deployment even when consumers would break
--notify
Opens a GitHub issue on each affected consumer repo and fires configured webhooks

Phase 2 recognises that breaking changes are sometimes intentional — a major version cut, a deprecation cycle. The flag pair gives teams an escape hatch that still leaves a paper trail. Consumer teams wake up to a GitHub issue, not a broken pipeline.

Live Verify

Static checks tell you the contract is compatible. Live verify tells you the consumer tests actually pass.

Safe to deploy.
Open question — Phase 3
How does CVT know when a consumer CI pipeline has finished? The callback mechanism and consumer consent model are not yet designed. This is the key design question for Phase 3.

This is the most important feature in the issue. A schema can be contract-compatible but still break a consumer's integration tests — because the tests encode real usage, not just the schema surface. Live verify closes that gap. The callback design is the open question we need to resolve.

The Contract File

What a consumer team commits to their repo.

.cvt/payments-api.yaml 
format: v1
consumer_id: checkout-service
consumer_version: 3.1.0
schema_id: payments-api
schema_version: "1.2.0"    # pinned, no ranges
environment: prod

used_endpoints:
  - method: GET
    path: /payments/{id}
    response_fields: [id, amount, currency, status]

  - method: POST
    path: /payments
    request_fields: [amount, currency]

Validation Rules

✓ format must be "v1"
✓ consumer_id, schema_id, schema_version are required
✓ schema_version must be valid semver — pinned only, no ranges like ^1.0.0 or >=1.0.0
✓ Each endpoint must have method and path. Method must be a valid HTTP verb.
⚠ consumer_version and environment are optional but warn if missing
⚠ Concrete paths like /payments/123 warn — use template /payments/{id}

Pinned versions are a deliberate design choice. Ranges like ^1.0.0 require semver range parsing and create ambiguity about what's actually being validated. Pinned versions are mechanically verifiable.

New CLI Commands

Four new commands ship in Phase 1a.

Terminal
# Scaffold .cvt/ directory structure
$ cvt init --mode consumer
  ▶ Created .cvt/payments-api.yaml (sample contract)
  ▶ Created .cvt/config.yaml
 
# Validate contract file format (shallow lint)
$ cvt lint .cvt/payments-api.yaml
  ✓ format: v1
  ✓ schema_version pinned: 1.2.0
  ✓ 2 endpoints valid
# Export a contract from SDK test interactions
$ cvt export-contract --consumer checkout-service \
  --schema payments-api --interactions ./test-results/
  ✓ Exported .cvt/payments-api.yaml (8 interactions → 3 endpoints)
 
# Show loaded contracts and versions
$ cvt status
  3 contract files · payments-api@1.2.0 · auth-api@2.0.0 · user-api@3.1.0

cvt lint is deliberately shallow — it validates the contract file format, not schema compatibility. That distinction matters: format validation is fast and local; compatibility checking requires the full engine.

⬡ Phase 2
Contract sources: repo://, discover://, multi · GitHub issue notifications · webhooks — needs separate design doc

--live-verify · exportContract() across all SDKs · callback mechanism and consumer consent model TBD

88 tests across Phase 1a

1. CompatibilityEngine rewrite 2. SchemaProvider + FetchVersion 3. Contract loading + validation 4. Offline can-i-deploy 5. CLI: init, lint, extended flags 6. E2E integration tests

The prerequisite is load-bearing. If we start Phase 1a before the CompatibilityEngine consolidation, we'll end up with two diverging implementations of the same logic. That's the one thing we cannot let happen.
