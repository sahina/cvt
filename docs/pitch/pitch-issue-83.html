SchemaRegistryProvider Interface

A single interface in pkg/cvt/ with two methods. Fetch a schema by ID, register that a consumer uses it. That's the entire contract between CVT and any registry.

Interface

pkg/cvt/registry.go 
type SchemaRegistryProvider interface {
    FetchSchema(
        ctx       context.Context,
        schemaID  string,
        version   string,
    ) ([]byte, error)

    RegisterConsumerUsage(
        ctx    context.Context,
        record ConsumerUsageRecord,
    ) error
}

type ConsumerUsageRecord struct {
    ConsumerID    string
    SchemaID      string          // info.title
    SchemaVersion string          // info.version
    Endpoints     []EndpointUsage
    TestResults   *TestResultDetail // Phase 2
}

Schema Identity

Source Maps To Example
info.title Schema ID (slug) pet-api
info.version Schema Version 2.1.0
--consumer Consumer ID order-service
CVT_CONSUMER_ID Consumer ID (fallback) order-service

--schema pet-api resolves via the registry provider. --schema ./file.json stays direct file read. The presence of --registry-api activates the provider.

The interface is minimal: two methods. Different organizations use different registries (homegrown, Backstage, Apicurio, SwaggerHub). The provider pattern lets CVT work with any of them. The POC ships a REST provider.

Consumer Testing Flow phase 1

What happens when a consumer runs cvt validate with the registry configured.

The flow is: fetch schema from registry, validate locally, report usage back to registry. Failed validations skip registration — you don't want broken consumers in the registry. CLI reports per-invocation (one POST per validate call). SDKs batch in Phase 3.

CLI in Action phase 1

When --consumer and --registry-api are both present, successful validation automatically registers consumer usage. No extra step, no separate command.

Today — local only

Terminal
$ cvt validate \
  --schema ./petstore.json \
  --interaction test.json
 
✓ Validation passed
 
 
No registry configured.
No consumer tracking.

With registry — implicit registration

Terminal
$ cvt validate \
  --schema pet-api \
  --schema-version 2.1.0 \
  --interaction test.json \
  --consumer order-service \
  --registry-api http://registry:8080
 
✓ Validation passed
✓ Registered order-service → pet-api

Typical CI pipeline — env vars set once

.github/workflows/contract-tests.yml 
env:
  CVT_CONSUMER_ID: order-service
  CVT_REGISTRY_API: https://registry.example.com/api/v1

steps:
  # Each validate call auto-registers on success
  - run: cvt validate --schema pet-api --schema-version 2.1.0 --interaction tests/get-pets.json
  - run: cvt validate --schema pet-api --schema-version 2.1.0 --interaction tests/create-pet.json
  - run: cvt validate --schema user-api --schema-version 1.0.0 --interaction tests/get-user.json

The left terminal is what exists today. The right adds two flags. Nothing breaks, nothing changes for teams that don't use the registry. Environment variables avoid repetition in pipelines with multiple validate calls. Flag precedence: flag > env var > error.

POC Registry API phase 1

Schema-centric REST API. Schemas are the top-level resource. Consumers register usage against a schema. No auth for the POC.

Central API Registry — REST Endpoints 
# Fetch schema by ID (used by FetchSchema)
GET    /schemas/{schemaId}/versions/{version}/spec
GET    /schemas/{schemaId}/versions/latest/spec

# Register consumer usage (called implicitly on successful validate)
POST   /schemas/{schemaId}/consumers
Body:  {
         "consumerId":    "order-service",
         "schemaVersion": "2.1.0",
         "environment":   "ci",
         "endpoints": [
           { "method": "GET",  "path": "/pets" },
           { "method": "POST", "path": "/pets/{id}" }
         ]
       }

# List consumers of a schema (for future can-i-deploy)
GET    /schemas/{schemaId}/consumers
Idempotent
Multiple POSTs for the same consumer + schema upsert the record
Schema-centric
Primary query: "who depends on this schema?" — a simple GET
No auth
Internal company registry. Consumer ID is sufficient identity for POC.

The API is minimal. CLI reports per-invocation — one POST per cvt validate call. The registry upserts, so repeated POSTs are safe. This is the POC implementation. The SchemaRegistryProvider interface abstracts over it.

Phase 1 Scope

What we're building and how the registration trigger works.

✓ SchemaRegistryProvider interface with FetchSchema + RegisterConsumerUsage
✓ POC REST API — no auth, no persistence guarantees
✓ Schema identity from info.title + info.version
✓ --consumer / CVT_CONSUMER_ID flag + env var
✓ --registry-api / CVT_REGISTRY_API flag + env var
✓ Implicit registration on successful validation only
✓ Backward compatible: --schema ./file.json still works

Registration trigger

--registry-api set + --consumer set + validation passes = register
--registry-api set + no --consumer = error
No --registry-api = just validate (no registration)

Implicit registration fires only on success. Failed validations do not register — no broken consumers polluting the registry. The presence of both --consumer and --registry-api signals intent. No ambiguity.
